## 二、阶段划分

### 阶段 0：无损软解收尾与提交（P0，本周）— ✅ 已完成复核与单测，待提交
目标：把当前工作区变成可回滚的干净基线。

1. **代码自审** `DspAudioTrackPlayer` 无损路径 +470 行 diff，三个重点的结论：
   - **有损回退边界**：原先内联在 `tryPrepareNativeLossless` 里、无法单测。已提取为
     `NativeLosslessDecoder.isNativeSupportedFormat(int)` 单一裁定点——只有 FLAC/WAV 下沉
     native；MP3 刻意不启用（系统有 `audio/mpeg` 硬解，软解白烧 i.MX6Quad 的 CPU）。
     附带确认一个**方向安全的误判**：ADTS AAC（`0xFF 0xF1`）会被帧同步掩码嗅成 `FMT_MP3`，
     但 `FMT_MP3` 不进原生软解，最终仍由系统硬解接手——错成「交给系统」而非「喂给 dr_*」。
   - **阻塞读与看门狗的相互作用**：`DspPlayer-OpenWatchdog`（15s）在 `finally` 里被
     `interrupt()`，成功/失败/异常三条出口都不会误伤已建立的管线，无冲突。但
     `BufferedHttpSource` 自身的断流检测在 JVM 单测里恒不触发（`SystemClock.elapsedRealtime()`
     被 `returnDefaultValues` 打成常量 0），**这条只能在实车/真机验**。
   - **断点精度回退**：`doNativeSeekInternal` 成功后按请求毫秒重算 presentation 时间戳，
     误差上限为一个 FLAC frame（4096 samples ≈ 93ms @44.1kHz），v2.3 #11/#28 的进度条不分叉
     契约未回退。**但 native seek 跑在渲染线程且无超时保护**：无 SEEKTABLE 的 FLAC 做
     `drflac_seek_to_frame` 需要回溯读，每次跨出 2MB 窗口都触发一次 Range 重定位下载，
     弱网下一次 seek 可能阻塞渲染线程数秒 → `stopRenderingThread` 的 `join(3000)` 超时。
     已加 `teardown done in Xms` 面包屑用于实车定位，转阶段 1 走表项（见下）。

2. **自审新发现并已修复的缺陷（BUG G，播放致命级）**：
   `HttpSourceReader` 只在 `seek()` 时调 `seekReadPos`，**顺序读推进时从不 `updateReadPos`**，
   读者登记位永久钉在起点。而 `writeToRing` 的窗口回收以「最慢读者的未读位置」为下界，
   于是 `bufStart` 永远滑不动、下载线程写满 capacity 后死等，与正在阻塞读的解码线程互相锁死。
   后果：**任何大于 2MB 窗口的无损曲目（几乎每一首 FLAC，20MB+）播完头部约 12 秒即卡死**，
   30 秒后 `readAt` 抛 `network stall` 收场。这与 8:40 现场「点了不播 / 卡死」高度吻合
   （若当时 v3 引擎已开）。对照组：`HttpProxyServer:307` 与全部 4 处既有 `BufferedHttpSource`
   单测都正确调了 `updateReadPos`，唯独 native reader 漏了，所以旧测试全绿也没发现。
   修复：在短读循环内每推进一块就 `source.updateReadPos(token, cursor + total)`
   （放在循环外不够——dr_* 单次就要几十 KB，一次大读足以跨过整个窗口）。

3. **补单测**（沿用现有 JVM 单测风格，JVM 用例 76 → **152**，全绿）：
   - `NativeLosslessPipelineTest#testSniffFormatBoundaries` / `#testNativeFallbackBoundary`：
     RIFF 非 WAVE、RIFF 不足 12 字节、大写 FLAC、`OggS`、3 字节 ID3、空数组、
     帧同步 `0xE0`/`0xDF` 低位边界、ADTS AAC 的安全误判方向；
   - `HttpSourceReaderTest`（10 例，真实 socket + 真实环形缓冲）：短读续读满、
     **窗口随读者推进回收**（BUG G 回归）、尾部余量短读、EOF 返回 -1、回溯 seek 重读原字节、
     同位 seek 零回源、非法位置拒绝、**abort 解开卡在断流源上的阻塞读**、abort/close 幂等、
     引用计数只归还一次。修复前 3 例超时，修复后全绿且套件耗时从 2m16s 降回 19s；
   - `LosslessBridgeTest`（18 例）：JNI 桥把 IOException / seek 失败 / seek 抛异常一律折叠成
     `0`/`false`（异常穿透 JNI 边界 = 进程级崩溃，回退就没机会发生）、EOF 的 `-1` 必须原样
     透传、destOffset 如实传递（写错会把上一块尾巴当音频喂进去 → 规律性爆音）、
     绝对字节位原样下传、`bridgeAbort` 幂等且不抛、null reader 容错；
   - 测试用 HTTP 源服务器提取为同包共享类 `TestHttpOrigin`，新增 `stallAfterBytes` 旋钮
     （送满 N 字节后挂死但不断开——这才是解码线程真正会被无限阻塞、必须靠 abort 解开的现场）。

4. **提交前检查**：`largeHeap` 已确认开启（`android:largeHeap="true"`），1.6GB 车机上与
   2MB 环形缓冲 + 64KB JNI 缓冲的总量相比余量充足，不构成 OOM 风险；NDK 双 ABI
   （armeabi-v7a + arm64-v8a）`.so` 体积增量待 `assembleDebug` 产物核对。
5. 提交建议拆两笔：`feat: v3 原生无损软解（dr_* 下沉 C++）` + `fix: ...`（如自审发现问题）。
   → 自审确有发现，第二笔为 `fix: 修复原生 reader 未推进窗口登记位导致大文件无损卡死`。

### 阶段 3：遗留问题清理（P1）— ✅ 三项已完成（2026-09-07，JVM 188/188 绿）
1. **EQ/音效设置持久化** ✅（`d284500`）：音效参数落 SharedPreferences，AudioPlayerService 起播时重放，沿用单飞/令牌收口规约。对应现场「重开 APP 后 DSP 音效自动关掉」。
2. **慢网 `-19` 循环退避** ✅：根因**不是**缺退避（假播放看门狗早有 6s→60s 指数退避 + 上限），而是 `(what=1, extra="-19")` 被判为不可恢复直接 `GIVE_UP`，于是每轮看门狗重启都复现一次错误 → Toast 与 `Log.e` 无限刷屏、且永远走不到重试。改法（策略全部落在无 Android 依赖的 `PlaybackStateMachine`，可 JVM 单测）：
   - `isTransientTransportError(what, extra)`：`-19` 归为可恢复传输层错误，进入既有三级重试阶梯（2 次直接重试 + 上限 3 次）；
   - `effectiveRetryAction(action, transientTransport)`：传输层错误的 `REAUTH_RETRY` 降级为 `PLAIN_RETRY`——重登录对传输层问题毫无意义，只会白等一轮 120s 鉴权冷却；`GIVE_UP` 不得被降级逻辑复活（有专门断言）；
   - `shouldNotifyError(streak)` + 服务端 `silentErrorStreak`：同一轮起播未成功期间只提示用户一次，重复错误降级为 `Log.w` + 面包屑；streak 与 `streamRetryCount` 在 5 处同时归零（`handlePrepared` / `playSong` / `playNext` / `playPrevious` / 未 prepared 时的恢复起播），下一轮仍有提示机会。
   - 新增 3 例 `PlaybackStateMachineTest`。实车抽查并入走表 #8。
3. **进程重启后列表短暂乱码** ✅：原假设（缓存加载完成前 UI 用了未修复元数据）**不成立**——网络解析侧 `JellyfinApiClient` 早已调 `TextRepair.repair`，缓存写侧 `saveSongs` 存的也是修复后文本。真正的漏洞在**读侧**：`SongDao.parseCursorToSong` 原样返回 cursor 值，于是修复逻辑上线前写入的旧行在进程重启后先读缓存即显示乱码，直到网络刷新覆盖 —— 正好是观察到的「短暂乱码」。改法：读侧对 `name/artist/album/genre/folder_name` 再套一层 `TextRepair.repair`；`TextRepairTest#repairIsIdempotentOnAlreadyRepairedText` 锁定幂等性（对已修复文本是恒等操作，双重修复安全）。
   - 残余（记录在案，不处理）：旧行的 `pinyin` 是按乱码文本算的，拼音搜索仍会漏；但下一次曲库同步 `saveSongs` 会整行覆盖，自愈窗口短。不做启动期一次性迁移——车机上多一次全表写事务不划算。

### 阶段 5：工程化加固（P2，持续）
1. **native 崩溃防护** ✅（2026-09-07，JVM 195/195 绿 + 模拟器全链路验过）：
   - **JNI 边界加固**：`native-lib.cpp` / `NativeLossless.cpp` 在 `Get*ArrayElements` 之前做越界/奇偏移/采样率声道范围校验并 `new(std::nothrow)`——JNI 里越界是 SIGSEGV 或静默堆破坏，Java 侧 `catch(Throwable)` 根本接不住，只能 C++ 先拦。
   - **归因**：会话标记扩为 `pid|startWallMs|engine`，引擎切换时重写；只有 `native_crash`/`java_crash` 且上次会话真在用 v3 才计数，`abnormal_exit`（划掉应用/LMK）绝不计数，否则日常关 APP 就能攒满熔断。
   - **熔断**：纯策略类 `NativeEngineGuard`（零 Android 依赖，可 JVM 单测）裁定；连续 3 次可归因崩溃 → `engine_v3_auto_disabled` 落盘，`AudioPlayerService.isV3EngineEnabled()` 据此回退系统 MediaPlayer。
   - **单向锁存（模拟器实测抓到的缺陷）**：首版按当前连击重算标志，熔断后引擎已换成系统、之后会话必然「不可归因」把连击清零，于是**用户正常关一次 APP 就让 v3 悄悄复活**，回到「一放歌就闪退」死循环。已改为锁存语义（`shouldAutoDisable(count, alreadyDisabled)`），只有设置页显式重开（`resetEngineGuard()`）能清除；回归用例 `aCleanSessionAfterTheBreakerTripsKeepsItLatched` 锁定。
   - **UI**：设置页按「有效态」（pref && !锁存）翻转，锁存时药丸显示 `系统 (崩溃保护)`（药丸改 wrap_content，58dp 定宽会裁字）；点击即重开并 Toast 说明原因，下一首歌起生效。
   - **顺带移除** `MainActivity.onCreate` 的 NativeDsp 自检块：它无视引擎偏好跑 native、烧冷启动 CPU、污染参数重放缓存，还会破坏崩溃归因。
2. **构建环境固化** ✅（2026-09-07，落在 `README.md` §7.3）：
   - 要求 JDK 17~21，实测 `JAVA_HOME=/opt/homebrew/Cellar/openjdk@21/21.0.9/...` 可用；JDK 25 下 Gradle 8.9 在 **daemon 启动阶段**就挂，`build.gradle` 根本没被 evaluate，所以「构建脚本自检 JDK 版本」这条路走不通，只能靠文档 + 用户级配置。
   - `gradle.properties` 是 git 跟踪文件，严禁写机器路径；`org.gradle.java.home` 覆盖请写到用户级 `~/.gradle/gradle.properties`。
   - 同时补记 NDK + CMake 双 ABI（arm64-v8a / armeabi-v7a）构建要求，避免漏装 NDK 时误判为代码问题。
3. **APK 体积红线** ✅（2026-09-07，量化完成，红线满足且余量 >4 倍）：v2.3.0 无任何 native lib，故 `.so` 全量即为增量。实测 debug 包（未 strip，属上限值）：`lib/arm64-v8a/libzspacecarplayer_dsp.so` 708,744 B（APK 内 deflate 后 278,257 B）、`lib/armeabi-v7a/…` 466,588 B（deflate 后 220,469 B），整个 APK 4,336,609 B。均远低于 <3MB/ABI 红线 → **dr_mp3 保留，不裁剪**（有损回退路径仍需要它，MediaCodec 在 8600 上不可信）。

## 五、8:40 现场事故复盘与涓流饥饿修复（2026-09-07 夜间补记）

### 5.1 事故与三根因
08:40 现场：切到粤语金曲点歌「还没播放」→ 点设置卡死闪退 → 重开 APP 发现 DSP 音效被关。三个症状三个根因：
1. **点了不播 / 进度冻结**：上游涓流（Cloudflare→NAS 链路间歇性只供几 KB/s）。旧断流检测只看下载侧「有无字节进展」（`STALL_TIMEOUT_MS` 30s）与 socket read timeout（15s）；涓流每秒挤几百字节也算进展、每次 read 都在 15s 内返回，两个检测器都不触发。2MB 环形缓冲被抽干后渲染线程永久 wait 在 `readAt`，UI 仍显示播放中——无报错、不切歌、不上报。
2. **点设置卡死闪退**：主线程阻塞型崩溃（拆机 reset 在主线程等渲染线程退出是高危窗口）。本轮已埋 `main_thread_blocked` 看门狗与面包屑（`reset begin` / `reset done`），下次复现可直接定界。
3. **DSP 音效自动关**：音效设置不持久化（阶段 3.1 提前修掉：落盘 + 启动即回放 `applyDspParamsToNative()`，崩溃重启后不再归零）。

### 5.2 修复设计：读者视角的涓流饥饿检测
- `BufferedHttpSource`：20s 滑动窗口（`STARVE_WINDOW_MS`）内读者累计挨饿 ≥18s（`STARVE_LIMIT_MS`）即判饥饿；判定函数 `starveVerdict` 为纯静态函数（JVM 可测，绕开 `SystemClock` 在单测里恒 0 的问题）。前两次判定只**强制重连**（epoch+1、断旧连接、窗口保留续算），第三次升级 `fatalError`；读位清空 / reset 时解除武装（防误报）。
- **如实报错链**：`HttpSourceReader.failed` → `NativeLosslessDecoder.hasStreamFailed()` → `nativeRenderLoop` 的 `framesGot<=0` 分支报 `onError(STREAM_STALL=-10002)` 并带断点毫秒——**不再伪装 onCompletion**（8:40「歌自己乱跳」的根除点；dr_* 把读错误折叠成 `readSamples()==0`，与真 EOF 同返回值，必须靠失败标志区分）。
- `HttpProxyServer.obtainSource`：带 `fatalError` 的源直接收割关闭（否则新读者复用死源、requestStart=0 落在旧窗口内，瞬间 IOException 堵死自愈）。
- `AudioPlayerService.handlePlayerError`：v3 负值错误码一律按可恢复处理 → 同歌断点重试（`NETWORK_RECOVERY`）。

### 5.3 验证记录（JVM 184/184 绿 + 模拟器证据链）
- **JVM**：新增 `StreamStarvationTest` 9 例（窗口武装/边界滚窗/含边界上限/累计结算/喂饱清零防误报/时钟回拨），合计 184 全绿。
- **模拟器（android-25，adb root）三段证据**：
  1. DNS 快失败（`svc wifi disable`）：15s 后 `native stream stalled … what=-10002` → 同歌断点重试。验如实报错与重试链（但走的是旧重试耗尽路径，非饥饿检测）。
  2. iptables 黑洞（OUTPUT DROP 80/443，连接活着但零供数）：旧连接 read timeout 进 retry；服务层 stall 看门狗 25s 重建连接；**恢复网络瞬间 `starve stall 1/2` 强制重连并自愈续播**——验检测器武装与重连分支。
  3. **自然间歇涓流**（上游故障复发，curl 同时测得 830KB/s 但存在 ≥18s 停供段）：完整升级链在真机抓到——`00:28:40 starve stall 1/2` → 供数恢复窗口清零（**防误报生效**）→ `00:29:20 1/2` → `00:29:40 2/2` → `00:30:00 starve fatal（3 windows）` → `what=-10002 @192426ms/237824ms` → 断点重试 → 续播后**真实播完**自然切下一首（与 8:40 假报切歌区分开）。
- 结论：检测、升级、防误报、如实报错、断点重试、自愈六种行为全部验到；FATAL 分支另有 JVM 单测兜底。

### 5.6 取证工具备注（模拟器）
- `svc wifi/data disable` 会让 DNS 立即失败（UnknownHostException），走旧重试耗尽路径，**模拟不出涓流**；黑洞（iptables DROP）保「连接活着但零供数」；真涓流最终靠上游自然故障复现。Mac 侧限流代理（`adb reverse` + guest nat REDIRECT，仅节流 `/Audio/` body）已备好作备选手段。
- UI 真值以截图为准（uiautomator 对设置面板盲）；Java 线程dump 用 JDWP+jdb。
- **别用 root 直接改 `shared_prefs/*.xml` 造状态**：`sed -i` 以 root 重写会换掉属主/SELinux 标签，应用随即「read without permission」+ `avc: denied { rename }`，读写全失败且现象极像应用 bug。必须改时补 `chown u0_aXX:u0_aXX` + `chmod 660` + `restorecon`；优先用真实操作路径（点击/崩溃注入）造状态。
- 注入 native 崩溃用 `adb shell kill -11 <pid>`，crash 缓冲区的 `Fatal signal 11` 行带应用 UID，重启后 `logcat -b crash` 仍可读到，归因链完整。
