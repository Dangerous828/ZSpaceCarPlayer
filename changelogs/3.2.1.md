| 1 | Retry | `fix` | 同曲直接重试加退避节奏：`PLAIN_RETRY` 不再是「错误一到就立刻重放」，改为第 1 次等 6s、第 2 次等 12s 再重放。此前三次尝试在两三秒内全部撞在同一个网络抖动上，把 `MAX_STREAM_RETRY_ATTEMPTS=3` 的预算烧光后 `GIVE_UP` 跳下一首，用户听到的是「歌自己跳了」；而蜂窝链路抖一下通常几秒就回来，原地多等反而比切歌更快——`dur=0ms` 的 FLAC 流式让下一首预取彻底失效，切歌等于零缓冲从头起播。「网络波动, 自动重试」提示提前到进入退避那一刻，保证等待开头就有解释 | 2026-10-05 |
| 2 | Retry | `fix` | 恢复动作收口为唯一拥有者：新增 `streamRetryBackoffPending`，看门狗的 `REBUILD_STREAM` 分支在退避挂起期间让位（与既有 `authWaitInProgress` 同一种表达方式）。此前两套定时器各自计时，退避链和看门狗会在同一时刻各起一次播放。取消点挂在 `startPlayback` 入口（所有起播路径的唯一入口，一并覆盖手动切歌 / 上下首 / 看门狗重建 / `GIVE_UP`）与服务释放处；退避 Runnable 内**先复位状态再校验 generation**，反写会在错误路径上留下 pending 标志让看门狗永久让位 | 2026-10-05 |
| 3 | Update | `fix` | 升级检查不再阻塞主线程：`ensureClient()` 的 TLS 底座装配（X.509 解析 + `TrustManagerFactory` 初始化，Android 4.3 上要好几秒）连同请求派发一起移入后台单线程 `update-check`。此前 `call.enqueue()` 的异步只覆盖网络段，装配仍发生在调用者线程（手动按钮与启动自动检查都在主线程），与类契约「整个过程不阻塞主线程」及设置页硬要求 3 相悖 | 2026-10-05 |

## ⏭️ 已知未修（vc12 当时快照，逐条收口状态见行尾）

> 本节是 vc12 当时的快照，**四条均已有最终归属**（收口版本或「有意不改」的结论），状态直接写在每条行尾。

1. `NATIVE_OPEN_TIMEOUT_MS` 15s 死线放宽或可配（`DspAudioTrackPlayer.java:44-6`）。实测频率是每 5.1 次起播 1 次而非「每首都跳」，且 `abort()` 只置取消标志、不杀连接，之后是回退系统 MediaCodec，收益有限。 → **vc15 收口**：没有走"放宽/可配"，判据换成环形缓冲有无进展（`BufferingPolicy.openShouldAbort`，15s 无进展才收手 + 45s 硬上限），慢但持续下载的开流不再被误掐。
2. `dur=0ms` 连带三处退化：prefill 门槛退化成 768KB + 7s 超时兜底、`isBufferingStable(-1,-1,-1)` 恒 false（满屏 `STUCK heartbeat percent=-1` 由此而来，不是真卡住）、`shouldPrefetchNext` 永不触发。同时 `prefill gate begin/reached/timeout` 只写 logcat 不进 breadcrumb，起播是否超时强行开播在上报里看不到。 → 三处退化**vc15 收口**（`IAudioPlayer.setKnownDurationMs` 把入库时长接回管线，缓冲进度与下一首预取恢复）；prefill 的 768KB 退化与 `lead` 在 `percent<0` 时返回 -1 两处**论证后有意不改**（FLAC ~100KB/s ⇒ 约 7.7s 领先量本就够；没有 contentLength 不硬造百分比）。`prefill gate` 结论进 breadcrumb 那半条**仍未处理**（`DspAudioTrackPlayer.java:498/511/519` 仍是 `Log.i/Log.w`），时长接回后只剩可观测性价值，跟进由定时任务「车机 vc15 升级与六项修复效果自动核验」承接。
3. 退避期间的 UI 可见状态（「重试中 N 秒」或复用缓冲指示）。 → **车主拍板不做**，静默期不改任何 UI，只留 Toast 与面包屑；这是决定不是欠账，无新要求不再重开。
4. 升级清单链路当日仍有超时样本（`[update] check failed` + `SocketTimeoutException`），TLS 校验失败近三日仅 1 例；`TlsCompat`「只增加信任锚、绝不放宽主机名校验」是刻意的不变量，未动。 → **不列为缺陷**：超时已有专属文案（`UpdateChecker.java:315-317`），且 vc12 起底座装配失败也走 `postError`、按钮不再卡在「检查中」；蜂窝网真超时属预期。`TlsCompat` 的不变量继续不动。
