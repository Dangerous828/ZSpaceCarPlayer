| 1 | Retry | `fix` | 同曲直接重试加退避节奏：`PLAIN_RETRY` 不再是「错误一到就立刻重放」，改为第 1 次等 6s、第 2 次等 12s 再重放。此前三次尝试在两三秒内全部撞在同一个网络抖动上，把 `MAX_STREAM_RETRY_ATTEMPTS=3` 的预算烧光后 `GIVE_UP` 跳下一首，用户听到的是「歌自己跳了」；而蜂窝链路抖一下通常几秒就回来，原地多等反而比切歌更快——`dur=0ms` 的 FLAC 流式让下一首预取彻底失效，切歌等于零缓冲从头起播。「网络波动, 自动重试」提示提前到进入退避那一刻，保证等待开头就有解释 | 2026-10-05 |
| 2 | Retry | `fix` | 恢复动作收口为唯一拥有者：新增 `streamRetryBackoffPending`，看门狗的 `REBUILD_STREAM` 分支在退避挂起期间让位（与既有 `authWaitInProgress` 同一种表达方式）。此前两套定时器各自计时，退避链和看门狗会在同一时刻各起一次播放。取消点挂在 `startPlayback` 入口（所有起播路径的唯一入口，一并覆盖手动切歌 / 上下首 / 看门狗重建 / `GIVE_UP`）与服务释放处；退避 Runnable 内**先复位状态再校验 generation**，反写会在错误路径上留下 pending 标志让看门狗永久让位 | 2026-10-05 |
| 3 | Update | `fix` | 升级检查不再阻塞主线程：`ensureClient()` 的 TLS 底座装配（X.509 解析 + `TrustManagerFactory` 初始化，Android 4.3 上要好几秒）连同请求派发一起移入后台单线程 `update-check`。此前 `call.enqueue()` 的异步只覆盖网络段，装配仍发生在调用者线程（手动按钮与启动自动检查都在主线程），与类契约「整个过程不阻塞主线程」及设置页硬要求 3 相悖 | 2026-10-05 |
| 4 | Update | `fix` | 补掉后台化引入的新竞态：装配期间 `inFlight` 尚未就位，用户此刻离开设置页时 `cancel()` 会打空、请求照旧发出并在之后回调。新增 `cancelled` 标志，后台任务在派发前后各查一次；底座装配本身失败也一律走 `postError` 回调，否则按钮卡在「检查中」直到 45s 看门狗 | 2026-10-05 |

## 验证

- host 单测全绿：**33 个结果文件 / 373 用例 / 0 failures / 0 errors**（2026-10-05 实跑，非 up-to-date 复用）。
- 新增边界用例钉在 `PlaybackStateMachineTest`：`plainRetriesWaitSixThenTwelveSeconds`（6s/12s，第 3 次与预算外为 0）、`backoffLadderWorstCaseSilenceIsEighteenSeconds`（最坏累计静默 18s，与 `MAX_STREAM_RETRY_ATTEMPTS` 之和钉死）。退避序列与看门狗的 6s 起点是**两条独立序列**，改一个不得带动另一个。
- `./gradlew testDebugUnitTest assembleDebug` BUILD SUCCESSFUL。`StreamTransport*` / `BufferingPolicy` / `StreamStarvation` 等不应受影响的 seam 均未变红。
- ⚠️ **发布用 debug 包**：`release` buildType 没有 signingConfig，`assembleRelease` 出的是无法安装的包；车机覆盖升级还要求与历史包同签名，故沿用 `-debug.apk` 口径。

## ⏭️ 已知未修（另开线）

1. `NATIVE_OPEN_TIMEOUT_MS` 15s 死线放宽或可配（`DspAudioTrackPlayer.java:44-6`）。实测频率是每 5.1 次起播 1 次而非「每首都跳」，且 `abort()` 只置取消标志、不杀连接，之后是回退系统 MediaCodec，收益有限。
2. `dur=0ms` 连带三处退化：prefill 门槛退化成 768KB + 7s 超时兜底、`isBufferingStable(-1,-1,-1)` 恒 false（满屏 `STUCK heartbeat percent=-1` 由此而来，不是真卡住）、`shouldPrefetchNext` 永不触发。同时 `prefill gate begin/reached/timeout` 只写 logcat 不进 breadcrumb，起播是否超时强行开播在上报里看不到。
3. 退避期间的 UI 可见状态（「重试中 N 秒」或复用缓冲指示）。当前 6s 静默的后半段无任何提示，需实车确认是否可接受。
4. 升级清单链路当日仍有超时样本（`[update] check failed` + `SocketTimeoutException`），TLS 校验失败近三日仅 1 例；`TlsCompat`「只增加信任锚、绝不放宽主机名校验」是刻意的不变量，未动。
