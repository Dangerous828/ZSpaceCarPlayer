# ZSpaceCarPlayer v3.1.4 Changelog

**版本：** v3.1.4 (versionCode 8)  
**更新日期：** 2026-09-22  
**适配系统：** Android 4.3 / API 18 (吉利 8600 经典固件)

> 多声道母带不再原样直传：源码率超链路能力时改由服务端下混成两声道 FLAC；断点续播彻底失败时不再无声无提示。

---

## 🐛 修复一：多声道曲目下载领先量被压死，全程可听卡顿

**现象**：车机播「答案」(id `bde3778eecb8429daf06059e4de26810`，44.1kHz / **7 声道**) 时点播控栏「上报」，2026-09-22 20:30、20:31、20:56 连点三次（中途还重启了一次进程）。

**证据**：把 77 条上报记录的 diagLog 按时间戳去重后比对起播后 90 秒的缓冲建立曲线——

| 会话 | 曲目 | lead 峰值 | 90s 内 percent |
| :--- | :--- | :--- | :--- |
| 09-22 18:47 | 盗将行 | 47s | 5 → 69 |
| 09-22 18:50 | 空空如也 | 48s | 5 → 57 |
| 09-22 19:40 | 童话镇 | 48s | 4 → 53 |
| **09-22 20:29** | **答案 (7ch)** | **2s** | **1 → 28** |

`lead` 是下载头领先播放头的秒数。立体声能冲到 47~48s，正是 8MB 环形缓冲 ÷ 176KB/s 的物理上限，说明下载一路跑赢播放；「答案」被压死在 2s，90 秒只下完 28%，净速率约 0.72× 实时——播放头始终贴着下载头，任何一点抖动都直接变成可听卡顿。

**实测**：`GET /Audio/{id}/stream.mp3?...&static=true` 对这首歌回 143,076,468 B / 232s = **616KB/s (4.93Mbps)**。车机蜂窝链路有效吞吐约 250~300KB/s，缺口 2 倍以上。

**根因**：3.1.3 的 `downmix 7ch->2ch` 只解决**进音效链路之后**的声道数，不解决**传输**——7 声道字节仍然要一个不少地拉过公网。

## 🔧 改动一：高码率源走服务端下混（`net/JellyfinApiClient.java`）

- 条目解析新增读取 `MediaSources[0].BitRate`（列表请求本来就带 `Fields=MediaSources`，零额外请求）。
- 码率 > **2Mbps** 的源，`stream_url` 改由 `getDownmixStreamUrl()` 生成：`/Audio/{id}/stream.flac?static=false&audioCodec=flac&audioChannels=2`。立体声 PCM 只需 176KB/s，仍走原来的直传路径，完全不受影响。
- **不掉音质**：FLAC 是无损压缩，不做有损量化；两声道裁定与 3.1.3 的客户端下混同口径，听感一致。实测整曲从 143MB 降到 **23,423,640 B = 101KB/s**，传输字节降到约 1/6.1。
- **为什么安全**：车机 v3 的流头嗅探认 `fLaC`，由 `dr_flac` 硬核软解，不会掉回系统 `MediaExtractor`——8600 缺 FLAC 解码，那正是修复二里 `Failed to instantiate extractor` 的同一条路。
- 传输方式写进 `stream_url` 本身，冷启动读 SQLite 缓存时靠 `audioChannels=2` 标记复原，**不需要 DB 迁移**。起播、下一首预取、预取作废三条路径统一走 `getStreamUrlForSong()`，保证预取与起播 URL 完全一致（不一致会让预取源命中失败、白占一份 8MB 缓冲）。

## 🐛 修复二：重试耗尽后既不出声也不提示

**现象**：断点续播时反复 `doPrepare failed: IOException: Failed to instantiate extractor.`，累到 `streak=3` 后落一行 `[play] error suppressed`，然后**什么都不再发生**——要等下次进程重启才会再试。用户看到的就是"点了没声、屏幕上也没有任何提示"。09-16「未来へ」、09-18「Baby」「Bad Romance」三次同一形状。

**根因**：`PlaybackStateMachine.shouldNotifyError()` 的判据是 `errorStreak <= 1`（防慢网下 Toast 刷屏），而重试预算 `MAX_STREAM_RETRY_ATTEMPTS = 3` 用尽才走 GIVE_UP——**走到 GIVE_UP 时 streak 必然已 > 1**，那句 `reportPlaybackError("播放出错...")` 因此永远被自己造的抑制逻辑吞掉。两个独立设计的防刷屏机制叠在一起，把"最终失败"变成了静默。

## 🔧 改动二：GIVE_UP 必须可见且不钉死会话（`service/AudioPlayerService.java`）

- 重试预算用尽时**绕过抑制**直接 `onError`，文案点明已跳过哪首歌；同时落 `GIVE_UP ... skip` 面包屑，下次上报能直接看出是被跳过的而非自然切歌。
- 跳过当前曲继续播下一首，并归零 `silentErrorStreak` / `streamRetryCount`：一首起播失败的歌不再能把整个播放会话钉死到熄火为止。

## 🐛 修复三（服务端）：上报重复入库与来源 IP 失真

`crash-ingest` 侧，与客户端改动无关但同批部署：

- **按 `reportId` 幂等**：09-16~09-22 的 77 行 JSONL 里只有 48 个唯一 `reportId`，28 个各收两份（`received_at` 差 0~3 秒）。重复那份不再落盘，但仍回 `{"ok": true}`——客户端据此删本地文件，否则它会按退避一直重投。任何按行数做的统计此前都会虚高一倍。
- **`source_ip` 不再记成 caddy 自己的 IP**：此前所有上报的 `source_ip` 都是反代对端，看起来像同一台机器发的。
- 实现收进 `home-hub/jarvis/deploy/crash-ingest/server.py` 作为权威源（此前只存在于 NAS，无版本管理）。

- **`source_ip` 改读 `CF-Connecting-IP`**：此前记的是 caddy 自己的容器网络 IP，所有上报看起来来自同一台机器。先按 `X-Forwarded-For` 首段实现，实测发现本端点经 CF Tunnel → caddy 两级反代，caddy 会把 XFF 换成自己看到的对端（`192.168.31.152`），仍然拿不到公网地址；`CF-Connecting-IP` 由 Cloudflare 写入且只含客户端真实出口 IP，改为主判据、XFF 退为无 CF 时的兜底。线上复核：从 Mac 投一条探针，落盘 `source_ip` 与 `ifconfig.me` 完全一致。
- 实现收进 `home-hub/jarvis/deploy/crash-ingest/server.py` 作为权威源（此前只存在于 NAS，无版本管理），并补可重跑的契约测试 `test_ingest.py`（纯 stdlib，`python3 test_ingest.py`，11 条）。

## ✅ 本地验证

- **host JVM 单测 339 条全绿**（新增 `net/StreamTransportChoiceTest` 9 条）：钉死 2Mbps 阈值的边界（立体声 1,411,200 bps 必须保持直传、7 声道 4,928,000 bps 必须转码、边界值 2,000,000 不含、BitRate 缺失回 0 时保持原行为）、下混 URL 必须是无损（断言不含 mp3/aac，防以后有人图省事换有损编码）、冷启动读缓存时能按标记复原传输方式且重新签当前 token。
- **服务端转码实测**：对「答案」(`bde3778eecb8429daf06059e4de26810`) 请求 `audioCodec=flac&audioChannels=2`，回 `200`、流头 magic `fLaC`（真 FLAC，非 RIFF 伪装），整曲 23,423,640 B / 232s = **101KB/s**；同一首直传是 143,076,468 B = 616KB/s。
- **`crash-ingest` 契约测 11 条全绿**：ack 永远是 JSON 不回 HTML；重复 `reportId` 只落一行但仍回 `ok:true`；**去重表跨进程重启仍生效**（重启后再投同一 id 仍判 duplicated）；`CF-Connecting-IP` 优先、XFF 次之、socket 对端兜底；超体积回 400 而非 502；非本客户端 UA 403；畸形 JSON 与数组体 400。
- **线上端到端复核**：公网投两次同一 `reportId`，落盘行数 77 → 78（只 +1），第二次回 `duplicated:true`；`latest.json` 的 `sha256`/`sizeBytes` 与其 `apkUrl` 实际下载字节逐字节一致。

## 🚗 实车验收清单

1. 车机设置页「检查更新」拉到 v3.1.4 (vc8) 并安装，`dumpsys package` 确认 `versionCode=8`。
2. 播「答案」(抖音热歌列表内，7 声道)，确认不再卡顿；上报日志应出现 `native pipeline up ... fmt=... ch=2`（而非 ch=7），且不再有 `downmix 7ch->2ch`——下混已在服务端完成。
3. 抽一首立体声 FLAC/WAV 回归：确认其 `stream.mp3?...&static=true` 直传 URL 未变、音量与音效无变化。
4. 找一首已知会失败的歌（如「Baby」）断点续播，确认重试耗尽后**屏幕上出现"多次重试仍无法播放，已跳过: Baby"**并自动继续播下一首。
5. 车机点一次「上报」，NAS 当日 JSONL 收到 1 行且 `source_ip` 是车机公网地址（不再是 `172.22.0.x`）。

## ⏭️ 已知未修（另开线）

1. `Failed to instantiate extractor` 本身：8600 系统 `MediaExtractor` 对某些容器缺解码器，本版只做"失败即跳过并告知"，未修根因（需要逐容器判定 v3 能否接管）。
2. AMP 功放唤醒重试（`Amp wake retry attempt=1/2`）与音量 index 12↔13 抖动。
3. 启动期主线程卡 6s（X.509 证书解析 + `SharedPreferences.awaitLoadedLocked`），属开机/刷新歌单时的 UI 卡，与播放卡顿不同一条线。
4. 服务端转码依赖 Jellyfin 容器内 ffmpeg 可用；若某次转码失败，该曲会走重试路径并最终跳过（修复二保证不再静默）。
