# 3.2.11 (vc22) — vc21 首份真车上报读出来的结论，与它暴露的仪表缺陷

依据：2026-10-08 19:03:57 车主在车上点的手动上报（`reportId=1a11b2f069b-bca1`，
`appVersionCode=21 / 3.2.10 / Android 4.3 / Neusoft GEELY`，`triggerSource=playback_bar`）。

## 一、这份上报证明了什么

1. **OTA 自动升级到 vc21 成立**：上报里就是 21，全程没连 adb。
2. **A1（取流回到单条顺序读）成立**：整首歌的字节绝大多数是从**一条**长连接上连续收下来的
   （`socket=5,209,600B` 而 `discarded=0B`），不再是一首歌拆成几十条请求。
   "是我写了什么东西把速度限到 100 多 KB"这条，到这里可以排除。
3. **这次卡顿是真·供给不足**，但**不是无损档天生不可用**：
   `bitrate deficit #1 required=212954B/s` —— 卡住的《广寒宫》需要 **213KB/s**。
   播放期间实际供给按 `percent` 序列算：起播 25 秒内 **367KB/s**（够用，`lead` 涨到 38s），
   随后 25 秒掉到 207KB/s（刚好贴平消耗，`lead` 不再涨），再掉到 156→**70KB/s**，
   `lead` 38s→29s→16s→10s→4s→0s，`buffering=true` 一路到上报点，
   logcat 同期密集 `AudioTrack releaseBuffer() ... disabled, restarting`（抽干后的欠载表现）。
   同一条链路起播时能给 367KB/s，所以**病因是蜂窝链路在播放中途掉速，不是取流形状**。
4. **这首歌为什么这么贵**：查服务端 `jellyfin.db`，
   `古风歌曲/广寒宫 - 丸子呦.flac`，`Size=45,343,898`、`RunTime=212.928s`、
   `MediaStreamInfos: flac / 48000Hz / 2ch / **BitDepth=24** / BitRate=1,703,633bps`。
   整夹 33 首（正好就是当时那个播放列表）：**16 首 ≥180KB/s、7 首 120~180、10 首 80~120、
   0 首 <80，平均 158KB/s，最重 216KB/s**，合计 1.2GB。
   这批本来就是 24bit hi-res FLAC（不是我 10-06 转的那批 16bit wav→flac，那批在欧美经典音乐）。
   24bit 的原始字节率是 288KB/s，FLAC 压到 0.74 ⇒ 213KB/s，**比 16bit 那批贵近一倍**。

## 二、这份上报暴露的仪表缺陷（本版全部修掉，否则下一次上报照样读不懂）

5. **同一首歌多条活动源时，指示器问错了对象**：`HttpProxyServer` 里 9 个单源查询
   （percent / bufferedBytes / socketBytes / contentLength / ringHasRoom / starving / fatalEver …）
   都是按登记顺序取**最早**那条，而重定位会分出 `url#fN` 的 fork 源、预取晋升也共用同一 URL。
   上报里相隔 0.8 秒的 `conns=4 socket=900627B` 与 `conns=1 socket=5209600B` 就是这么来的——
   两行问的压根不是同一条流，"0.8 秒收了 4.3MB"这种荒谬读数纯属取错源。
   现在统一走 `findReporterLocked()`：**先比读者数（有读者=正在喂播放），并列比下载头，再并列取最先登记的**。
   选取规则是纯函数 `pickReporterIndex()`，三条单测钉住。
6. **`conns` 会往回退**：代理侧的求和只统计"还活着"的源，旧 fork 一关读数就变小，
   会让人把"取错源"读成"这首歌只用了一条连接"。服务侧改为按 URL 归属记**累计最大值**，
   切歌复位；同时新增 `srcs=`（这笔账摊在几条源上）。
7. **`ctx_prefetchSocketBytes` 标签错**：它取的是 `getUpstreamCost()[1]`，那一项是
   **discardedBytes**，不是 socket 字节。所以上报里 `prefetchConns=1 prefetchSocketBytes=0`
   真实含义是"预取建了一条连接、作废 0 字节"，而"预取到底收了多少字节"从没被量过。
   现在 socket 单独问代理，`discarded` 另立 `ctx_prefetchDiscardedBytes`。
   这是我上一批"预取代价进仪表"里的一处没做完——预取有没有抢带宽，当时其实判不了。
8. **水位行没有身份**：`watermark: buffered=8192KB/8192KB rate=465kbps` 两行既不知道是哪条源说的，
   也没写窗口是否饱和。而**窗口贴满时 `rate` 不等于链路速率**（下载线程被背压卡住，它只会等于
   消费速率）——类注释原先还写着"rate 单调偏低指向供给不足"，在那种时刻会把消费侧/背压误读成带宽不足。
   现在带 `src= refs= hasRoom= head= tail=`，判读注释按上面重写。
9. **A2 的写路径完全不可观测**：`disk=` 只报了"从盘上喂出去多少"，第一次播必然是 0，
   于是**从上报里分不清"边播边存根本没落盘"和"落了盘但这首是第一次播"**。新增 `stored=` 与
   `ctx_diskStoredBytes`。

## 二·五、同一晚追加的一条：磁盘缓存写盘压在了读者的锁上（我自己的回归）

车主又点了一次上报（21:40《Wrap Me In Plastic》、21:41《Dream It Possible》），里面出现一个
只可能是我方造成的形状：**`watermark: buffered=8192KB/8192KB`（窗口满）与 `lead=0s`、音频一顿一顿
同时成立**。字节都在 RAM 里，读者却拿不到。查下来是 vc21 的 A2 落盘写法：

10. **`writeToRing` 在 `synchronized(lock)` 里直接 `disk.record(...)`**，而这把 `lock` 正是原生
    解码器 `readAt` 取字节要拿的同一把。等于<b>每 64KB 就往读者的通路上插一次闪存写</b>；更要命的
    是提前落账那次里面还带 `getFD().sync()`。原注释写的是"闪存的毫秒级写入换一个不会读脏数据的
    保证，值"——这个判断被今晚的上报推翻了：停顿是会听得见的。
    改法：锁内只做一次 `Arrays.copyOf` 暂存，落盘挪到锁外由同一条下载线程按序消费。正确性不丢：
    下载线程只有一条，写的是"这段字节属于这个绝对位置"，晚一点落地内容仍是同一份数据，区间表也只
    认确实写成功的位置。另外 `fsync` 只在 `close()` 那一次做，提前落账不做——掉电丢账本的代价是
    重建缓存，热路径上等闪存的代价是卡顿。
    同一次上报里的另一条读数（《Dream It Possible》`buffered=1334KB~2077KB/8192KB`、治理器
    `est=67,883B/s` 而 `required=112,843B/s`）**不是**这个形状：窗口远没满、三口径同向，那首是
    确确实实的链路掉速。所以今晚两种成因并存，这条改完才有办法把它们分开判。

## 三、这一版没做的（都是需要车主点头或需要真车的，不是遗漏）

- **古风那 16 首 ≥180KB/s 的 24bit FLAC 怎么处理**：三条路各有代价，我不替你选——
  ① 车上手选「流畅」档（这台服务端实测固定 256kbps≈32KB/s，任何蜂窝都够）；
  ② 库侧把 24bit 降到 16bit/48k 重压 FLAC（约降到 100~120KB/s，**相对现在的文件是有损**，
    虽然 16bit 也是通行的 CD 规格）；③ 维持不动，承认这批 hi-res 只在到家 WiFi 那种带宽下可靠。
  要不要动、动哪批，等你说。（**自动降档已被你否决，我不会把它做成自动的。**）
- 环形窗从 8MB 加大：8MB 在 213KB/s 下只有 38s 余量，加大确实能扛更久的掉速，但堆占用是
  本项目碰过红线的地方（`BufferingPolicy.MAX_SOURCES` 注释里那句"曾触碰堆红线"），
  要动得在车上实测 RSS，不能凭算。
- FLAC 无 seektable 的二分迭代成本（vc21 已落"越界 seek 判不可达"这把安全刀，B/C 两案仍等真车数据）。
