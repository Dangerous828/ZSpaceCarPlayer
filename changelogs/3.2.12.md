# 3.2.12 (vc23) — R3 纯时长起播门槛（消除 13s 静音）与 R6 自适应缓冲目标

依据：2026-10-08 晚对齐 QQ 音乐车机版（ThumbPlayer2）与喜马拉雅车机版（libxmediaplayer.so minSdk 11）一手架构实测。

## 一、本次改动重点

1. **R3 纯时长起播门槛（消除 13s 静音）**：
   - 旧逻辑：起播必须攒够 `min(5s × 所需速率, 窗口 12% 即 ~1.0MB)`，在 68KB/s 弱网下需等待约 14.8 秒静音。
   - 新逻辑：对齐主流播放器（Media3 / QQ 音乐），只要积攒达到 **1.2 秒音频时长**（`LEAD_TARGET_START_SECONDS = 1.2f`）即可快速起播。在 68KB/s 弱网下仅需约 3.8 秒，大幅缩短起播白屏与静音等待。
   - 接入点：`DspAudioTrackPlayer` prefill 循环中接入 `BufferingPolicy.shouldFastStart(...)`，配合日志标记 `fastStart=`。

2. **R6 自适应缓冲目标时长（按窗口容量夹紧，不作为阻断门槛）**：
   - 纯函数 `adaptiveBufferTargetSeconds(linkRateBytesPerSec, requiredBytesPerSec, windowCapacityBytes)`。
   - 针对 8MB 环形窗物理容量上限严格执行 `min(目标秒, 窗口容量 / 所需速率)` 夹紧，绝不虚报无法达到的蓄水指标（如 24bit FLAC 下 45s 需要 9.6MB）。
   - 供给充裕（`linkRate >= requiredRate * 1.15f`）时维持常态 20s 目标；供给不足时在窗口物理允许范围内提高蓄水期望（至多 45s），仅用于 UI 建议与蓄水调节，**严禁作为起播或恢复播放的阻断门槛**，避免把"卡一下"变成"永久等待"。

3. **发版合规与配套对齐**：
   - 同步 `JellyfinApiClient.CLIENT_VERSION = "3.2.12"`。
   - 更新文档 `docs/stream_refactor_assessment_20261008.md`：纠正起播时长收益的客观表述（14.8s → 3.8s），并在 V3 架构节显著标注「状态：设计目标，未实施」。

## 二、副作用与实车观察点

1. **二缓冲概率（Rebuffer）**：起播仅攒 1.2 秒音频时长，若后续网络持续大幅低于所需码率，`isBufferingStable` 可能会较快判回 buffering，UI 可能会短暂闪烁"缓冲中"。
2. **预取触发窗口**：`maybePrefetchNext` 依赖 `lead >= 15s`，快速起播初期 lead 秒数较小，需等平稳播放一段蓄水后才会放行预取。
3. 以上两项需结合真车实际蜂窝网络上报进行观测验证。
