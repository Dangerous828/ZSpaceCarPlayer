# ZSpaceCarPlayer v3.1.3 Changelog

**版本：** v3.1.3 (versionCode 7)  
**更新日期：** 2026-09-20  
**适配系统：** Android 4.3 / API 18 (吉利 8600 经典固件)

> 修复 5.1 多声道曲目在车机上播放刺耳的问题：多声道母带进音效链路前先下混成立体声。

---

## 🐛 修复：多声道母带（ch=6）刺耳

**现象**：抖音热歌歌单里播「多幸运」声音刺耳，同一歌单其他歌正常，切到下一首立刻恢复正常。上报日志显示这首歌是 `sr=44100 ch=6` 的 5.1 WAV（RIFF/WAV，v3 native lossless 直解），前后歌曲全是 `ch=2`。解码、prefill、AudioTrack start 全程无报错，因此"日志零异常"是表象。

**成因**：三处叠加——

1. `DspEngine.h` 的 `DspEngine::process()` 只有 `channels == 2` 与 `channels == 1` 两个分支，ch=6 时**一个样本都不处理**，EQ / 低音 / 声场 / 混响 / 限幅整块透传；`native-lib.cpp` 的 `MAX_CHANNELS = 8` 又放行了 ch=6 的 init。
2. `AudioTrack` 只建成了 mono/stereo（系统不支持 6 声道裸 PCM 轨）。
3. 渲染循环按**母带**声道数计算写入长度，把 6 声道交错数据喂进立体声轨。

结果：每个输出立体声帧的 L/R 实际取自 `FL/FR → FC/LFE → BL/BR` 三帧一循环。`scripts/verify_ch6_downmix.mjs` 的实测——相邻样本跳变均值 **22.4 倍**（25618 vs 1144）、同样内容被拉成 **3 倍时长**（进度条与听感脱节）、LFE 被送进全频单元。相位抵消 + 每 3 帧换一次声道，即"刺耳"。

## 🔧 改动

**新增 `player/PcmDownmix.java`**（纯 Java，零 Android 依赖）

- 权重取 ITU-R BS.775 的 Lo/Ro 式：`L = FL + 0.707·FC + 0.707·环绕 + 0.5·LFE`，R 对称。0.707 是等功率声像法则。
- **LFE 按 0.5 并入而非丢弃**：车机没有独立低音炮，LFE 只能由全频单元发声，丢弃会让 5.1 母带低频偏薄；但 LFE 常是大动态纯低频，按 0.707 并入会把下级 BassBoost 推到频繁限幅。
- 索引 3 只在 `channels >= 6` 时按 LFE 计权；3/4/5 声道布局里那是又一个环绕声道，按 0.707 计权。
- **Q13 定点**累加：8 声道全满幅同相时最坏 1.35e9，仍留在 int32 范围内（Q14 会溢出，溢出不是异常而是静默错值）。
- 超过 0.95 满幅走 **tanh 软膝**（`KNEE = 31129`，与链尾 `SoftLimiter.h` 的 threshold 与曲线同参），不做硬钳位——硬钳位留下的陡边在 int16 域已丢失波峰信息，链尾限幅器救不回来。
- `short[]` 与 `byte[]` 两个入口共用同一份权重，数学逐样本一致。
- 边界闸：`channels` 不在 3~8、`frames <= 0`、src/dst 容量不足一律抛 `IllegalArgumentException`，由渲染循环转成 `DECODE_FAILED` 上报——比"继续放刺耳声"可见。

**接线 `player/DspAudioTrackPlayer.java`**

| 位置 | 改动 |
|---|---|
| `renderChannels` 字段 | 与 `channelCount` 分开：PCM 读取缓冲必须按母带声道数分配，不能跟着缩 |
| `initAudioTrackAndDsp()` | 全链路唯一下混裁定点；`NativeDsp.init` 与 AudioTrack 的 `channelConfig` 都改读 `renderChannels`；留 `downmix 6ch->2ch sr=…` breadcrumb 与 `CrashMonitor` 上下文，下次上报能直接看出下混是否生效 |
| `nativeRenderLoop()` | 循环外分配同等帧数的立体声 scratch 复用；顺序为 `readSamples → toStereo → processShorts → write` |
| `codecRenderLoop()` | MediaCodec 回退路径同样下混（6 声道 AAC 也会踩雷）；**分块改为整帧对齐**——8192 对 6 声道不整除，切在帧中间会让下混读到半个样本 |
| `INFO_OUTPUT_FORMAT_CHANGED` | 播放中途声道数变化时同步重算 `renderChannels`，scratch 置空交下一轮按新帧长重分配 |

`DspEngine.h` 与 JNI 缓冲约定未动：Java 侧保证只向 DSP 传 1/2 声道。

## 📱 Android 4.3 兼容性

新增代码只使用 API 1 级别的构造：`java.lang.Math`（`round` / `tanh` / `min` / `sqrt`）、基本数组与定点整数运算、`StringBuilder` 隐式拼接。无 lambda、无 Stream / `java.util.function`、无 try-with-resources 之外的新语法糖，也不依赖 core library desugaring。`AudioTrack.write(short[], int, int)` 与 `MediaCodec.INFO_OUTPUT_FORMAT_CHANGED` 均为 API 1~16 已有。

Android 4.3 的真实约束本来也不在这里：裸 PCM 直写 AudioFlinger、绕开系统 Virtualizer/Reverb 是 v3 引擎的既有设计，本次只改喂给它的数据形状。

## 🧪 验证

1. **JVM 单测**：新增 `PcmDownmixTest` 12 例，全量 **330 例全绿、0 skipped**（原基线 318 未破）。覆盖单位激励权重表、中心声像不偏移、全通道满幅不回绕、7.1 累加余量、byte/short 双入口逐样本一致、src/dst offset、容量不足必抛、`ch <= 2` 与 `ch > 8` 必拒、膝区单调与连续扫描。
2. **突变验证**（确认断言有判别力）：LFE 权重 0.5 改成 1.0 → 单位激励用例失败；软膝起点从 `KNEE` 改回满幅 → 膝区连续性用例在 `amp=19195` 精确失败。两处均已复原。
3. **回归等价**：`ch=1` / `ch=2`（绝大多数歌）路径逐值等价——`needsDownmix` 为 false 时下混缓冲不参与、写入长度仍是 `framesGot * channelCount`；`effectiveChannels(1)=1`、`effectiveChannels(2)=2` 与原 `channelCount == 1` 判定同结果；codec 路径 ch=1/2 时帧对齐后的分块上限仍等于原来的 8192。
4. **电平分布**：按真实母带分配（FL/FR −6dBFS、FC −8、LFE −14、环绕 −12，每通道独立相位，20 万帧）扫描 headroom——不预留衰减时峰值 1.13~1.17 满幅，**越过满幅的样本仅 0.01%，越过 1.35 满幅的 0%**，全部落在软膝可覆盖的浅度超载区。据此**不加预衰减**：−3dB 会让 5.1 曲目比同歌单的立体声曲目明显轻，而收益接近零。
5. **静态检查与包内实证**：`lintDebug` 的 `NewApi` 全仓仅 1 条命中，落在既有的 `update/UpdateInstaller.java:180`（API 26 的 `canRequestPackageInstalls`，有运行时分支保护），本次新增与改动的两个文件**零命中**；两条 lint error（`ui/SongAdapter.java` 的 RecyclerView 与上述 NewApi）均为改动前既有项。`aapt2 dump badging` 实测包内 `minSdkVersion:'18'`、`targetSdkVersion:'28'`、`versionCode='7' versionName='3.1.3'`；`classes.dex` 内确认存在 `PcmDownmix`。`assembleDebug` 与 `testDebugUnitTest` 全绿。
6. **实车**：本次发布**尚未实车复验**，验收清单见下。
