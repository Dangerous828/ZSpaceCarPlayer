# 3.2.10 (vc21) — T1 基准重审后的第一批：取流架构 + 档位 + 磁盘缓存

日期：2026-10-08。背景与完整差距分析见 `docs/audit_t1_baseline_20261008.md`（本次重审的产物）。

**这批不发版**（车主指令：全部都做完才 commit；发版另行点头）。versionCode 已推进到 21。

## 起因：一个我错了三轮的判断

车主连着几轮给的是同一个反证：「我下载这个包 3m 也才不到 10s，你跟我说网速不行？」
这一版做了对照实测，把"链路只有 60~90KB/s"这个结论**推翻**：

| 同一首歌同一时刻同一热点 | 结果 |
|---|---|
| 一条长连接取 5MB（`Range: 0-5242879`） | 797 KB/s（传体阶段），首字节 1.44s |
| 同样 5MB 拆成 20 段各 256KB | 133 KB/s |
| 20 段复用同一条 keep-alive 连接 | 一样慢（133KB/s）——代价在**每请求一次首字节**，与建连无关 |

也就是说我此前拿来论证"必须降档"的 60~94KB/s，量的很可能是自己的取流形状而不是链路。
绝对速率同日还测出过 246KB/s（波动 3 倍），所以只有**比值**可以引用。

顺带一条自纠：上一轮我说"实测到 2MB/s"并不存在——上报里 `api_key` 是 `[REDACTED]`，
照它拼的 URL 全部 0 字节。任何"我实测到 X"都必须先证明探针真拿到了字节。

## 修了什么

1. **越界 seek 判不可达**（`NativeLosslessDecoder.HttpSourceReader`）。旧实现只校验 `<0` 与
   `MAX_LIMIT`，越过文件末尾照样返回 true，于是把 **dr_flac 自己的"到流尾了、该收紧折半上界"
   判据废掉了**（`dr_flac.h:5888`），无 seektable 的二分只能靠整帧解码失败驱动，实车迭代约 9 次，
   而每次跳读落到窗外就是一条新上游连接 + 0.8~1.4 秒。总长未知（chunked）时保持放行，行为不变。
2. **前向小缺口改为等待**（`BufferedHttpSource.readPlacementAction`，阈值 256KB）。旧判定把
   "下一秒顺序下载就会送到"和"真跳走了"混成一回事，都去清窗重连。
3. **摘窗宽限期**（`shouldKeepFillingWhileIdle`，8 秒）：读者短暂离开时下载线程继续在同一条
   上游连接上收字节，不再一摘窗就 `disconnect()`。防回声条款写在判定里——`refCount>0` 才允许，
   所以切走的旧歌会**立刻**收手，不会在后台吃新歌带宽；`pumpIntoRing` 与 `writeToRing` **必须用
   同一条判定**，否则一边放行一边判死，宽限就是空话（第一版就漏了 writeToRing 那侧）。
4. **磁盘缓存**（新类 `StreamDiskCache`，A2）：边播边存，回拖/重播同一首/FLAC 跳读回落的老位置
   **就地从盘给，一条上游连接都不建**。三条硬约束：键 = `itemId + 总长`（**绝不含 api_key**，
   token 每次登录都换）；只读区间表确认的连续段，**跨洞一律不读**（把没下过的字节当数据交出去
   会表现为"歌里冒杂音"，比卡顿难查十倍）；chunked 转码流没有总长一律不缓存。LRU 按 mtime、
   只删自己前缀的文件，上限 1GB，仍在 `getCacheDir()` 下沿用 `CacheSizeManager` 的裁剪口径。
5. **音质档位**（新类 `StreamTier` + 设置页「音质」行，A3）：两档循环（无损 / 流畅），持久化，
   **只影响下一首，没有任何自动切换路径**——自动降档已被车主否决（治理器里的档位状态与 `AUTO_DEGRADE_ENABLED` 已整个删除，
   ，`StreamRateGovernor` 的类注释里记了他的原话与两次翻车的理由）。放弃当前曲时若正处于无损档，只在文案里给一句出口
   （"可在设置把音质切成「流畅」"）；服务端已无此曲那种失败不提这句，换码率也变不出那首歌。
6. **仪表补齐**：连接数改为**每次尝试都计**（旧口径只在 `getInputStream()` 成功后 +1，等于漏掉
   最该看见的重连风暴）；新增每请求首字节耗时（最近/最大/平均）与盘上命中字节，进
   `upstream conns=… ttfbMax=…ms disk=…B` 面包屑与 `ctx_upstreamConns` /
   `ctx_upstreamDiscardedBytes` / `ctx_upstreamTtfbMaxMs` / `ctx_diskServedBytes`。

## 一条实测纠正了档位标签

同一首歌试了七种码率写法（`maxStreamingBitrate` 128000/320000、`audioBitRate`、大写
`MaxStreamingBitrate`、`enableTranscoding=true`、加 audioCodec+采样率），**返回字节数完全相同**：
5,819,950B = **256.1kbps**。这台 Jellyfin 的 mp3 转码固定 256k、忽略码率参数。所以流畅档的真实
代价是 31.3KB/s（仍只有无损 101KB/s 的约 1/3），**用户可见文案一律写实测值，写 128 是假广告**；
原先那条按"128k = 16KB/s"断言的单测也跟着改成按实测常量断言。

## 明确不在本批（有据可查，不是遗漏）

- **A1 后续 B/C**：夹紧 `dr_flac` 的 `byteRangeHi`、或注入合成 seektable。要改 vendored 文件或
  C++ 内存布局（无 seektable 时 `pExtraData` 预留空间为 0，直接写就是堆越界），且 C++ 侧
  无任何自动化覆盖（`changelogs/3.0.0.md:41-42`：只能真车 seek 验），夹紧错误会退化成
  "顺序扫完整首"比现状更糟。等车上 `upstream conns` / `ttfbMax` 复测数据再决定。
- **代理 keep-alive：已判定不做**。v3 原生路径由 `DspAudioTrackPlayer:241-242` 直接
  `acquireSource()` 后交给 JNI 读，**不经过本地代理 socket**；`HttpProxyServer:485` 的恒
  `Connection: close` 只作用于 MediaCodec 回退分支，改了不改善主路径吞吐。
- L4 功能补齐 31 项（gapless/封面/歌单/睡眠定时/24bit/离线下载…）：独立一轮，不混进架构改造。

## 第二批（同版本内，按"没有不完整的部分"补齐）

7. **回退闸 `StreamTuning`**：取流改造动的是所有播放都要走的地基，而真车只有一台又看不到现场日志，
   所以四条改动各配一把闸，出问题在设置页关掉即可退回 vc20 行为，**不用重出包**：
   摘窗保连宽限、前向小缺口等待、越界 seek 判不可达、磁盘缓存。设置页新增「取流优化」「播放缓存」
   两行；缓存行同时显示占用/上限并给「清空」（关掉缓存会顺手清掉已存字节，不在设备上留没人用的东西）。
   判定仍是纯函数（闸作为入参），所以"关掉必须精确退回旧行为"被单测钉住。
8. **曲库边界**：`JellyfinApiClient.hasVideoStream` 按 `MediaStreams[].Type == "Video"` 滤除，
   实测本库 236 条是 4K/60 帧 mp4（h264+aac，单曲需 3.6MB/s），在车上永远播不动。
   判据用流类型不用码率猜；**MediaStreams 缺失一律放行**（宁可放一首慢歌进来，不许误杀真歌）。
   刷新后会明示"已滤掉 N 条带画面的文件"——不让用户自己发现"歌怎么变少了"。
9. **随机模式"上一首"修复**（`ShuffleHistory`）：旧实现 `playPrevious` 在随机模式下也是
   `new Random().nextInt(size)`，按下去会跳到任意一首（多数是往后），观感就是"上一首坏了"。
   现在 back/forward 双栈，"上→下"能回到原处；队列一变即清空（存的是下标，不清会跳错歌）。
   单测抓到两处实现边界：空栈 `goBack` 会抛越界异常且抛前已污染 forward；均已在实现侧修。
10. **睡眠定时**（`SleepTimer` + 设置页行）：到点**立即暂停**（不是"播完这首"——人睡着之后
    再唱完一整首更吵）；用 `elapsedRealtime` 口径，墙钟被车机同步改掉也不误判；剩余时间在
    副标题倒计时。
11. **拔出耳机/断开外放即暂停**：运行时注册 `ACTION_AUDIO_BECOMING_NOISY`（4.3 清单里声明无效），
    仅在"确实在播"时暂停并给一句状态，静止态不打扰。

**判定为不适用或缺依据（写清楚，不冒充完成）**：封面=车主 3.2.0 主动删除；服务端搜索=本仓已是
全量镜像 + 本地拼音搜索，1051 条没有"目录太大"的问题；多服务器=只有一台 NAS；逐字歌词=Jellyfin
只有行级数据；MediaSession/AAOS=4.3 无此 API；**响度归一化=实测这台 Jellyfin 的 1051 条
完全没有 `Normalization`/`Loudness` 字段**，没有可信增益值就不做猜测式音量拉平；
**离线下载**需要你先定交互入口与存储位置（列表/播放页目前没有任何长按菜单可挂），属新特性不列本批欠账。
完整逐项判定见 `docs/audit_t1_baseline_20261008.md` §4。
## 第三批（同一版本内，仪表与文案补漏）

12. **预取源的代价原先完全不可见**：`getUpstreamCost()` 按 URL 前缀聚合，而预取源的 key 是
    **下一首**的 URL，所以"预取有没有跟当前曲抢带宽"根本没有数据（我自己上一轮承认过的盲区）。
    现在服务侧记住 `prefetchedNextUrl`，让位时面包屑带 `pfConns/pfSocket/pfDisk`，
    当前曲的 upstream 面包屑同时输出 `ctx_prefetchConns` / `ctx_prefetchSocketBytes`。
13. **错误文案不再漏异常原文**（L5 里我们能做的那一半）：`无法加载音频流: + e.getMessage()`
    曾把 `java.io.IOException: Failed to allocate component instance` 这种英文句子打到车机屏幕
    上——车主既不知道发生了什么也不知道该做什么。现在给"无法播放《X》，请重试或换一首"，
    异常仍在 Log 与 breadcrumb 里，取证不损失。`STATE_ERROR`/MediaSession 那一半 4.3 无 API，
    仍是客观限制。
