## 三条判据分别治什么，验收时别混

流畅档（第 4 条）治的是**码率追不上**——`Dream It Possible` 需 110 KB/s 而链路只给 67 KB/s。它治不了**链路不通**：`你的世界` 已经是有损 16 KB/s 还卡，那种只能靠第 6 条的快速失败 + 重连缩短静音时长，换档救不了它。第 1~3 条又是第三类——服务端已经明确回答 404，只有曲库重同步换 Id 才有救。三种形态在上报里各有各的串，别用一种的改善去宣布另一种也好了。

判定链的接线方式：`BufferedHttpSource` → `DspAudioTrackPlayer.isResourceGone()`（新增到 `IAudioPlayer` 接口，系统播放器实现恒返回 false，因为它没有这条可读通道）→ `PlaybackStateMachine.effectiveRetryAction(action, transientTransportError, missingResource)` 新增第三参，**优先级最高**，命中即 `GIVE_UP`。

## 有意不改的两处

**`getStreamUrl()` 里写死的 `.mp3` 后缀不动**（`JellyfinApiClient.java:148`，`/Audio/{id}/stream.mp3?...&static=true`）。它看着像缺陷——FLAC 源却请求 `.mp3` 路径——但实测证伪：Jellyfin 在 static 模式下直接回原文件字节，`Content-Range` 带总长度，响应体魔数仍是 `fLaC`，只有 `Content-Type` 错成 `audio/mpeg`；而车机是靠 sniff 头 16 字节选解码器的（`ctx_sniffBytes=16`），MIME 不参与判断。实测三形态对照（同一 flac 条目）：`stream.mp3?static=true` → 206 + `fLaC`；`stream.flac?static=true` → 206 + `fLaC`；`/Items/{id}/original.flac` → **404 不存在这个端点**。历史上 `static=true` 也已成功过 44 次。改成"按源容器生成后缀"只是把一条已验证可用的路径换成没验证过的。

**`403` 不当终态**：它可能是权限/Token 问题（`AUTH_RETRY` 那条路本来就为它存在），和"资源不存在"不同源，误判成终态会把可恢复的会话问题变成跳歌。同理 `408/429` 虽是 4xx 但语义是"现在不行、等一下也许行"，必须继续重试——这两条都写进了单测断言。


## 流畅档的两处刻意取舍

**判据用固定速率下限，不用"该曲所需码率"**。后者需要每首的 `sizeBytes`，而它不在车机的曲库缓存里 —— 加一列就意味着一次 SQLite 迁移。本库无损曲码率本就均匀（实测 110~126 KB/s），一个带 ~15% 余量的固定下限（140 KB/s）更简单，也少一个"算得出但不准"的输入。

**seek 只作废速率窗口，不推翻档位**。拖动进度条会让累计偏移跳变（正向 seek 造出假高速率、往回拖造出负速率），所以 `seekTo()` 里调 `rebaseWindow()` 重建基准；档位本身是**链路属性**，seek 不改链路，若在这里做全量 `reset()` 就等于用户每拖一次条，降级状态被洗一遍、又要重新等 15 秒才判回来。

## 验证

- Host 单测：**389 条，0 失败**（本轮从 376 涨到 389：10 条 `StreamRateGovernorTest` + 2 条终态用例 + 1 条 `zeroByteOpenDiesSoonerThanSlowOpen`；`openWatchdogKillsOnlyStalledOpens` 同步补 `gotFirstByte` 第四参）。关键几条：`sustainedSlowWindowsDegrade`（连 3 个 60KB/s 窗口才降级）、`oneGoodWindowResetsTheStreak`（慢-快-慢-慢 **不得**降级，吸收抖动）、`hysteresisBandChangesNothing`（140~175KB/s 滞回带内不回升）、`stalledDownloadCountsAsSlow`（零进展按慢计，否则 `buffered=0B` 那种开流永远不会触发降级）、`thresholdsLeaveLosslessNoHeadroom`（下限必须 > 126KB/s、回升阈值必须 > 降级下限、流畅档必须 < 60KB/s —— 把"阈值不能是拍脑袋"钉成断言）。
- 一处测试自我纠正：新写"时长接回"用例时先断言了 `isBufferingStable(-1,-1,0)` 为 false，与实现不符（剩余 0 秒属「已不足一个稳定领先量」，按稳定处理），已按实现的真实语义改为 assertTrue。另一处 API 自我纠正：`StreamRateGovernor.onProgress` 最初按"增量"设计，测试写起来发现第一个窗口会重复计数，改成**累计口径**（正好就是 `bufEnd` 本身）。这两条记在这里是为了提醒：**新断言必须先对齐实现，别把期望当事实**。
- 出包：**3,126,331 B**（vc15 是 3,124,523 B，压缩内容只 +1,810）。`aapt2` 核 `versionCode=16 versionName=3.2.5`；dex 里新串 `resource gone terminal`、`gone on server, skip`、`曲目已不在服务器`、`start on smooth tier`、`-> smooth(128k)`、`maxStreamingBitrate`、`no-first-byte=`、`stalled no-progress=`、`deadline=` 各命中 1，旧措辞 `native open blocked` 计数 0，vc15 的 `retry backoff wait=`／`tls-warmup`／`duration unknown in container` 全部仍在 —— **装 vc16 一次拿全九项**。
- **核验 dex 时要按片段搜，别按整串搜**：新判死面包屑是运行时拼出来的（`"native open " + why`），dex 里存的是片段，按 `native open no-first-byte=` 整串 `grep` 得 0，差点被我读成"改动没进包"。这条与 2026-10-05 那条 `grep -c` 单文件无前缀导致全 0 是同一族坑：**计数为 0 先怀疑探针**。
- **一次差点被骗的构建陷阱（第三次踩同一坑）**：本轮某次出包得到 **5,157,896 B**，逐条目对比后发现压缩内容合计与正常包只差 1,810 B、`.so` 与条目数完全一致——**多出的 2.03MB 全是 zip 对齐填充**（正常包填充 78,630）。这正是本仓 README 早就记着的同一条：**增量构建会产出体积异常 (~5.1MB) 的包**，vc5 与 `code8-incremental-2` 两次都是它。我最初把它归因成"两个 task 一起跑"，读了 README 才知道成因是没 `clean`，已按事实改正。结论照旧：**发版一律 `./gradlew clean :app:testDebugUnitTest :app:assembleDebug`，并核填充量**；别把打包差异当成内容变化去查代码——多 2MB 在 67 KB/s 的链路上就是多下 30 秒，不是免费的。
- 构建环境：本机默认 `java` 是 JDK 25，Gradle 8.9 会报 `Unsupported class file major version 69` 且**留下上一次的旧 APK**（只看文件存在会把旧包当新包）。须 `JAVA_HOME=<openjdk@21>`。没有为此改 `gradle.properties`（那是全仓配置，会影响别人和 CI）。

## 实车判据（等车主试听后一并看）

升级后在曲库里放一首"文件已被改名/删除"的曲目，期望上报里：

> 注意场景可得性：车机在 2026-10-06 17:18 已重同步（`updatePlaylist size=134`），此后**同一会话里再没出现过 404**，所以这条判据不是随时可验的——要验就临时把某首歌在服务端改名制造 404，或等下一次曲库侧改名/删除。

1. **不再出现** `download retry N/5 … HTTP 404`（终态后根本没有第 2 轮）；
2. 出现面包屑 `resource gone terminal: resource gone: HTTP 404`；
3. 出现 `gone on server, skip <曲名>` 且**当场跳下一首**（不隔 6s/12s）；
4. 屏幕提示是「曲目已不在服务器, 已跳过」，而不是「多次重试仍无法播放」。

流畅档这条反而**有现成场景**：放 `Dream It Possible`（23,021,268B / 204s，需 110 KB/s，实测链路 67 KB/s），期望：

5. 约 15 秒后（3 个 5s 窗口）出现 `bitrate tier ->smooth(128k) est=…KB/s`，且**下一首**起播带 `start on smooth tier id=…`；
6. 换档后 `lead` 不再贴 0（16 KB/s 的需求对任何蜂窝链路都有富余），`starve stall` 不再出现；
7. 音效听感应与无损一致（EQ/Bass/声场/混响仍在，见 `DspAudioTrackPlayer.java:905`）——这条**只有耳朵能判**，需要车主确认；
8. 链路回到 175 KB/s 以上并稳住约 25 秒后，出现 `bitrate tier ->lossless`，再下一首回无损。

第 6 条（零字节快速失败）的判据：**升级前**那类 `native open stalled no-progress=15004ms ... buffered=0B` 应当**消失**，同现场改约为 4 秒的 `native open no-first-byte=…ms total=…ms buffered=0B`；有首字节的慢流仍按 15s 判（即升级后 `no-progress` 那条里 `buffered` 不该是 0B）。静音时长应从 15s 缩到 4s 左右——这条**体感明确**，车主能直接确认。
