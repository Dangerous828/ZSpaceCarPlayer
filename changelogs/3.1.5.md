# ZSpaceCarPlayer v3.1.5 Changelog

**版本：** v3.1.5 (versionCode 9)  
**更新日期：** 2026-09-23  
**适配系统：** Android 4.3 / API 18 (吉利 8600 经典固件)

> 无损 PCM 一律由服务端出 FLAC 再传；车机缓存不再自己排第二套顺序；播放列表只有一份真源。

---

## ⚠️ 先记一笔：上一版的判据字段根本不存在

v3.1.4 用 `MediaSources[0].BitRate` 判"这源码率喂不喂得起"。实测本机 Jellyfin 在列表接口返回的 `MediaSources` 里**不带 BitRate**（801 首全缺，该字段只在嵌套的 `MediaStreams[].BitRate` 里），取出来恒为 0，于是判据恒假——**那一版的传输策略实际一次都没触发过**，全库仍按原样直传。车机 09-23 08:38 上报里「出山」的 URL 仍是 `stream.mp3?...&static=true`，就是这件事的证据。

教训写进这里：**判据依赖的字段必须先确认它在真实响应里存在**，不能按 Jellyfin 文档假定的 DTO 结构推断。

## 🐛 修复一：立体声 PCM 直传同样没有余量

**现象**：2026-09-23 08:38 播「出山」(44.1kHz / **2ch** / WAV)，车机卡住，用户 08:39 点播控栏「上报」。

```
08:38:52  [buffer] percent=5  buffering=true  lead=10s
08:38:53  [buffer] percent=6  buffering=true  lead=10s
（此后 17 秒 percent 一动不动）
```

立体声 PCM 的字节率 176KB/s，而蜂窝链路有效吞吐实测约 250~300KB/s——只差 1.5 倍，任何并发流量或信号抖动都会把领先量吃光。**问题不是声道数，是未压缩 PCM 这个形态本身。**

**判据改为**：`MediaSources[0].Container` 属于未压缩 PCM 系（wav/wave/pcm/aif/aiff/aifc/raw/sun/au）时**不分声道数一律**请服务端出 FLAC；其余编码按字节率 >300KB/s 才动。字节率由 `Size / RunTimeTicks` 算（这两个字段实测一定在）：

```java
sourceBytesPerSec(143_076_468L, 2_316_887_070L) == 617_538L   // 「答案」7ch，实测值
```

**覆盖面实测**（本机曲库 801 首，按 app 同样的查询取回）：`Container=wav` 570 首，其中 **532 首落在立体声 PCM 档 (170~180KB/s)**、3 首落在多声道档 (>300KB/s)。也就是说这一改覆盖全库三分之二的曲目，此前它们全都在贴着链路能力直传。

**不掉音质**：FLAC 是无损压缩，不做任何量化；不涉及声道数变化时（立体声）连下混都不加。实测「God Is A Girl」：

| | 传输字节 | 字节率 | 流头 |
| :--- | :--- | :--- | :--- |
| 直传（原行为） | 38,817,450 | 176,529 B/s | `RIFF` |
| 服务端 FLAC | 27,625,876 | **125,629 B/s** | `fLaC` |

降 **28.8%**，且**逐字节验证为无损**：把服务端 FLAC 用 ffmpeg 解回 PCM，与原 WAV 的 `data` 段前 8MB `cmp` 完全一致（`BYTE-IDENTICAL`），44.1kHz/2ch/16bit 两端一致。车机 v3 的 sniff 认 `fLaC` 头、由 `dr_flac` 硬核软解，不会掉回系统 `MediaExtractor`（8600 缺 FLAC 解码，正是 `Failed to instantiate extractor` 那条路）。

**多声道才下混**：字节率 >300KB/s 时额外带 `audioChannels=2`，与 v3.1.3 客户端下混同口径，听感一致。

**要付的代价**：转码由 NAS 侧 ffmpeg 现算，实测吞吐 3.15MB/s（约为所需的 25 倍），性能不是问题；但**起播首字节会多等约 0.7~3.6 秒**（冷启动首次 ffmpeg 拉起 3.6s，随后 0.74s）。这是用起播延迟换播放期不掉带，符合"卡顿优先"的取向。

## 🐛 修复二：同一个歌单存在两套顺序（影子列表）

车机 SQLite 读侧此前一律 `ORDER BY name ASC`（`SongDao.getAllSongs` / `getFavoriteSongs`），而 SQLite 对 TEXT 的 `name` 序是 **Unicode 码点序**；服务端返回的是 Jellyfin 的 `SortName` 序。两者不同序（实测：服务端第一首「出山」，码点序第一首「38度6」）。

后果是同一份曲库在车上以两种顺序并存：

- 播放队列 = `setPlaylist` 挂载瞬间的顺序快照；
- 左侧列表在联网刷新后走 `filterSongsByCategory(allSongsList, …)` = 缓存的码点序。

于是"下一首"与左侧下一行不再对应——就是实车反馈的**"播放没有跟左侧列表走"**。

**改法：缓存不再自行排序。** `songs` 表新增 `sort_index`（DB v5，`onUpgrade` 加列），写入时记录服务端返回的位置，读侧统一按 `sort_index` 排；未写入过的旧行 (`-1`) 一律沉到末尾并按 `name` 稳定兜底。「播放最多」保留 `play_count DESC` 作主序（那是用户主动选择的排名视图，不是同一列表的第二套顺序），次级序换成 `sort_index`。

**列缺失时必须降级，不能赌迁移成功**：`sort_index` 靠 DB v5 的 `onUpgrade` 追加，而该仓历史上真出现过"升级漏加列导致整批回滚"(v4 的 `pinyin`)。若列不在而读侧仍按 `sort_index` 排，`SQLiteException` 会被现成的 catch 吞成**空列表**——表现成"曲库凭空全空"，比顺序不对严重得多。因此 `SongDao` 先用 `PRAGMA table_info(songs)` 探测一次并缓存结果：有列才按 `sort_index` 排、才写该列；没有就退回 `name ASC` 且不写列，功能退回旧行为而不是清库。

**同时清掉幽灵曲目**：逐条 upsert 的写入永不删除服务端已下架/改名的条目，车机库里因此长期留着取不到流的行——它们照旧出现在列表里，播到就表现为卡住或无声。现场对照：车机队列 size=**60**，而服务端「抖音热歌」现在只有 **55** 首。媒体库刷新成功这条路径改用 `saveLibrarySnapshot()`：事务内清空后按序整批重写（`play_count` 事先读出保留，歌词与进度是独立表不受影响）。逐条 `saveSongs()` 语义原样保留，供非全量场景使用，避免误删。

## 🐛 修复三：上报里的 `playlistIndex` 是陈旧值

该字段此前只在 `setPlaylist` 写一次，`playNext` / `playPrevious` / 刷新后的 `updatePlaylist` 都不更新，于是上报永远显示开机那一刻的位置（09-23 那次显示 51，而实际已推进 9 首并回绕）。任何人据此判断"列表有没有跟上"都会得出错误结论——包括本次排查的第一版结论。现在三处切歌/刷新点都会刷新该上下文，`updatePlaylist` 也补了带 index 的面包屑。

## 🚗 实车验收清单

1. 设置页「检查更新」拉到 v3.1.5 (vc9)，`dumpsys package` 确认 `versionCode=9`。
2. 播任意一首 WAV 歌（库里 570 首都是），上报日志里 `ctx_streamUrl` 应为 `/Audio/<id>/stream.flac?...&static=false&audioCodec=flac`，且立体声歌**不带** `audioChannels=2`；`native pipeline up` 之后应出现 `sniff fmt=1`（FLAC）而不再是 `fmt=2`（WAV）。
3. **起播会慢约 1~4 秒**（首次转码拉起 ffmpeg），确认这个等待可接受；播起来之后不应再出现"percent 长时间不动"。
4. 连续自然切歌 5 首，核对左侧高亮行与实际播放歌是否同一行；上报里 `ctx_playlistIndex` 应随切歌递增（不再是开机时那个定值）。
5. 冷启动后先播一首，再等一次联网刷新完成，然后按方向盘「下一曲」，确认播的就是左侧当前行的下一行。
6. 「抖音热歌」列表数量：刷新一次后应从 60 变 55（幽灵条目被清）。若刷完仍是 60，说明那 5 首服务端仍在，把它们在列表里等播到看是否能播——那是另一条线。

## ⏭️ 已知未修（另开线）

1. 起播多等 0.7~3.6 秒：可考虑对已知 PCM 曲目预取转码流，或让 Jellyfin 侧缓存转码产物。
2. `Failed to instantiate extractor` 的根因（8600 系统 MediaExtractor 对个别容器缺解码器）仍只做"失败即提示并跳过"。
3. AMP 功放唤醒重试与音量 index 抖动。
4. 启动期主线程卡 6s（X.509 证书解析 + `SharedPreferences.awaitLoadedLocked`）——开机/刷新歌单时的 UI 卡，与播放卡顿不同一条线。
